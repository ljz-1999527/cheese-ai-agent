# 基础篇 —— 必考不丢分


## 一、Java基础


### 1. HashMap的底层原理？和Hashtable、ConcurrentHashMap有什么区别？

**参考回答：**

存储结构：数组+链表+红黑树（JDK1.8后，链表长度>8且数组>64时转红黑树）。

put流程：计算hash → 定位槽位 → 空则插入，非空则遍历链表/红黑树，存在则覆盖，不存在则尾插。

扩容机制：默认16，负载因子0.75，扩容为2倍。扩容时重新计算每个元素的位置，这也是为什么容量必须保持2的幂次方——hash取模运算可以用位运算`(n-1)&hash`替代，速度更快。

和Hashtable区别：HashMap允许null key/value，线程不安全；Hashtable不允许null，线程安全但锁整表，并发性能差。

和ConcurrentHashMap区别：JDK1.8后ConcurrentHashMap用CAS+synchronized锁头节点，锁粒度更细，并发度更高。写操作只锁当前操作的桶（链表/红黑树的头节点），读操作基本无锁。


### 2. JVM内存模型是怎样的？垃圾回收机制了解吗？

**参考回答：**

内存区域：堆（存对象实例）、方法区（类信息/常量/静态变量）、虚拟机栈（每个线程私有，存局部变量和方法调用）、本地方法栈、程序计数器（记录线程执行位置）。

堆的分代：新生代（Eden+S0+S1）→ 老年代 → 永久代/元空间。新生代用复制算法，把存活对象从Eden和S0复制到S1，清空Eden和S0。老年代用标记-清除或标记-整理算法。

GC：Minor GC（新生代）频繁发生；Major GC（老年代）触发条件更严格，发生时会STW（Stop The World）。垃圾回收器：G1（JDK1.9默认，兼顾吞吐量和停顿时间），ZGC（低延迟，JDK11+）。

结合你的简历：EHR系统性能优化时遇到过频繁Full GC问题，通过分析heap dump发现定时任务创建了大量临时对象，调整了新生代大小后解决。


### 3. 线程池的核心参数有哪些？任务提交流程是怎样的？

**参考回答：**

七个核心参数：
- corePoolSize：核心线程数
- maximumPoolSize：最大线程数
- keepAliveTime：非核心线程存活时间
- unit：时间单位
- workQueue：阻塞队列
- threadFactory：线程工厂
- handler：拒绝策略

提交流程：核心线程未满→创建核心线程执行；核心线程已满→放入队列；队列已满→创建非核心线程；非核心线程也满→执行拒绝策略。

线程池的四种拒绝策略：AbortPolicy（默认，直接抛异常）、CallerRunsPolicy（由调用线程自己执行，适用于不能丢任务的场景）、DiscardPolicy（直接丢弃新任务）、DiscardOldestPolicy（丢弃队列里最老的任务，把新任务加进去）。

结合你的简历：大易API对接中间件用了CallerRunsPolicy，因为数据同步不能丢，线程池满了就让主线程自己执行。


### 4. 线程池的拒绝策略有哪些？

| 策略 | 行为 | 适用场景 |
|------|------|----------|
| AbortPolicy（默认） | 直接抛RejectedExecutionException | 能接受失败告警的场景 |
| CallerRunsPolicy | 由调用线程自己执行，压力回退到调用方 | 不能丢任务的场景（如数据同步） |
| DiscardPolicy | 直接丢弃新任务，不抛异常 | 允许部分数据丢失的场景（日志上报） |
| DiscardOldestPolicy | 丢弃队列里最老的任务，把新任务加进去 | 实时性要求高的场景 |


### 5. 什么是CAS？它有什么问题？

**参考回答：**

CAS（Compare And Swap）是一种乐观锁技术，通过比较内存值是否等于期望值来决定是否更新，是原子操作，由CPU指令支持。

三个问题：①ABA问题——值从A变B又变A，CAS误判为没变过。解决方式：用版本号或时间戳，如AtomicStampedReference；②自旋开销——失败时循环重试，高并发下消耗CPU；③只能保证单个变量的原子性——多个变量需要AtomicReference或synchronized。

结合你的简历：ConcurrentHashMap底层就是CAS+synchronized，比单纯用synchronized锁整个表效率高很多。


### 6. 什么是AQS？ReentrantLock和synchronized的区别？

**参考回答：**

AQS（AbstractQueuedSynchronizer）是Java并发包的基础框架，维护一个volatile int state和等待队列。ReentrantLock和Semaphore都是基于AQS实现的。

synchronized和ReentrantLock的区别：
- synchronized是JVM关键字，由JVM管理锁升级（偏向锁→轻量级锁→重量级锁），非公平
- ReentrantLock是API实现，支持公平锁和非公平锁，可中断，支持Condition和超时等待


## 二、Spring


### 7. Spring Bean的生命周期？

**参考回答：**

1. 实例化（new对象）
2. 设置属性（依赖注入）
3. BeanNameAware → setBeanName()
4. BeanFactoryAware → setBeanFactory()
5. ApplicationContextAware → setApplicationContext()

7. @PostConstruct / afterPropertiesSet() / init-method

### 8. Spring事务的传播行为有哪些？

| 传播行为 | 说明 |
|----------|------|
| REQUIRED（默认） | 有事务加入，没有新建 |
| REQUIRES_NEW | 挂起当前事务，新建独立事务 |
| NESTED | 嵌套事务，外层回滚内层也回滚，内层回滚外层不一定回滚 |
| SUPPORTS | 有事务加入，没有就非事务运行 |
| NOT_SUPPORTED | 非事务运行，有事务则挂起 |
| MANDATORY | 必须有事务，没有抛异常 |
| NEVER | 必须非事务运行，有事务抛异常 |

结合你的简历：工资上报模块里用REQUIRES_NEW把操作日志独立开新事务，主事务回滚了日志也要保留。


### 9. @Transactional失效的场景？

**参考回答：**

①方法不是public的（代理无法拦截private方法）
②同类内部调用（没走代理，直接调用this.xxx()）
③异常被catch了没往外抛，或者抛了非RuntimeException但没指定rollbackFor
④数据库引擎不支持事务（如MyISAM）
⑤事务传播行为配置不当（如配置了NOT_SUPPORTED或NEVER）


### 10. Spring Boot自动配置原理？

**参考回答：**

@SpringBootApplication包含@EnableAutoConfiguration，后者通过@Import导入AutoConfigurationImportSelector。这个Selector从META-INF/spring.factories（Spring Boot 2.7之后是META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports）里加载所有配置类，再通过@Conditional条件注解判断是否满足加载条件（如类是否存在、配置是否启用），满足条件则创建Bean注入容器。


## 三、MySQL


### 11. MySQL索引的数据结构？为什么用B+树？

**参考回答：**

InnoDB用B+树。叶子节点存数据，非叶子节点只存索引。B+树的非叶子节点不存数据，一页能放更多索引，树更矮，IO次数更少。叶子节点形成有序链表，适合范围查询。

为什么不用B树：B树每个节点都存数据，树更高，百万级数据要20+次磁盘IO。
为什么不用红黑树：红黑树高度logN，百万级数据要20+次磁盘IO，不适合磁盘存储。
InnoDB页大小默认16KB，B+树每个节点可以存储约1000个索引条目，三层树能存10亿+数据。


### 12. SQL调优怎么做？

**参考回答：**

先看执行计划（EXPLAIN），重点关注：
- type：ALL全表扫描要优化，至少做到range/ref级别
- rows：扫描行数，越少越好
- Extra：Using temporary临时表/Using filesort文件排序要优化
- possible_keys和key：实际用到了哪个索引

然后针对性加索引或重构SQL。

结合你的简历：月结优化时，发现考勤明细表的日期字段没建索引，加了复合索引后扫描行数从100多万降到几千行，同时把游标逐条循环改成基于临时表的批量集合运算，耗时从12分钟降到4分钟。


### 13. 事务隔离级别？

**参考回答：**

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|----------|------|-----------|------|
| 读未提交 | ✅可能 | ✅可能 | ✅可能 |
| 读已提交 | ❌ | ✅可能 | ✅可能 |
| 可重复读（MySQL默认） | ❌ | ❌ | ✅可能 |
| 串行化 | ❌ | ❌ | ❌ |

MySQL通过MVCC机制实现可重复读——每行数据维护创建版本号和删除版本号，事务启动时生成快照，查询只读可见版本的数据。


### 14. 聚簇索引和非聚簇索引的区别？

**参考回答：**

聚簇索引的叶子节点存整行数据（InnoDB主键索引），非聚簇索引叶子节点存主键值，查完整数据需要回表。一个表只能有一个聚簇索引，非聚簇索引可以有多个。

InnoDB的数据文件本身就是按主键组织的B+树，数据物理存储顺序和主键顺序一致，所以主键查询速度最快——一次B+树查找就能拿到完整数据。


### 15. 回表和覆盖索引？

**参考回答：**

回表：用普通索引查，叶子节点存的是主键值，需要再到聚簇索引里查一次完整数据。

覆盖索引：索引里已经包含了查询需要的所有字段，不需要回表。所以`SELECT *`通常比`SELECT 索引字段`慢。用`EXPLAIN`看Extra列是否有`Using index`来判断是否覆盖。


### 16. 索引失效的场景？

**参考回答：**

①对索引列使用函数或计算（`WHERE DATE(create_time) = '2026-08-30'`）
②隐式类型转换（`WHERE emp_id = '1001'`，emp_id是int）
③LIKE以%开头（`WHERE name LIKE '%张'`）
④OR查询中部分字段无索引（改UNION）
⑤复合索引未使用最左前缀（比如索引是`(a,b,c)`，只查`b`或`c`）
⑥索引列参与计算（`WHERE age + 1 = 30`）


## 四、Redis


### 17. Redis的数据结构有哪些？

**参考回答：**

- String：普通KV，Token缓存、验证码
- Hash：对象存储，用户信息
- List：队列、栈，消息队列
- Set：无序集合，去重、标签
- Sorted Set：有序集合，排行榜、延时队列
- 进阶：Bitmap（签到统计）、HyperLogLog（UV统计）、Geo（地理位置）


### 18. 缓存穿透/击穿/雪崩的区别和解决方案？

**参考回答：**

- **穿透**：查不存在的数据，缓存和库都没有 → 布隆过滤器过滤不存在的key、缓存空值（短时间过期）
- **击穿**：热点key过期，大量请求打到DB → 互斥锁（setnx）、逻辑过期（永不过期，后台异步刷新）
- **雪崩**：大量key同时过期 → 过期时间加随机值、Redis集群、多级缓存（本地+分布式）


### 19. Redis持久化方式？

**参考回答：**

RDB：定期生成全量快照，恢复快，但可能丢数据（两次快照间的修改）。

AOF：记录写操作日志，数据更安全，但文件大恢复慢。AOF有三种同步策略：always（每次写入都同步）、everysec（每秒同步，默认）、no（由操作系统决定）。

生产环境一般同时开启RDB做灾备、AOF保证数据安全。RDB的触发频率不宜过高（避免性能开销），AOF的rewrite机制可以控制文件大小。


## 五、RabbitMQ


### 20. RabbitMQ怎么保证消息不丢失？

**参考回答：**

三个环节：
- 生产者：开启confirm确认机制（消息到达Exchange后回调确认）
- Broker：队列和消息设置持久化（durable: true），消息写入磁盘
- 消费者：手动ACK（autoAck: false），业务处理完再确认

高并发下开启持久化对性能有影响，重要数据（订单、支付）必须持久化，日志类数据走异步确认模式，吞吐量优先。


### 21. 延迟队列怎么实现？用在什么场景？

**参考回答：**

RabbitMQ两种方式：①死信交换机+TTL——消息设存活时间，过期后自动进入死信队列被消费；②延迟队列插件——每条消息指定延迟时间，到期自动路由。

结合你的简历：EHR电子合同到期提醒——合同生效时往延迟队列发消息，延迟时间=合同期限-30天，到期自动触发提醒HR续签。


### 22. RabbitMQ的工作模式有哪些？如何选择？

**参考回答：**

| 模式 | 结构 | 适用场景 |
|------|------|----------|
| 简单模式 | 1生产者→1队列→1消费者 | 点对点异步任务 |
| Work Queues | 1队列→多个消费者（竞争消费） | 负载均衡，多个worker抢任务 |
| 发布/订阅（Fanout） | 1生产者→Exchange→多个队列 | 广播通知 |
| 路由模式（Direct） | 按routingKey精确匹配 | 按级别路由（ERROR走单独通道） |
| 主题模式（Topics） | 按routingKey通配符匹配（*和#） | 多条件路由 |

选型原则：先看业务场景需要什么，再选最简模式，不用复杂模式解决简单问题。


## 六、Spring Cloud / 微服务


### 23. Spring Cloud Alibaba组件有哪些？分别解决什么问题？

**参考回答：**

| 组件 | 解决的问题 |
|------|-----------|
| **Nacos** | 服务注册发现 + 配置管理（替代Eureka+Config） |
| **Sentinel** | 流量控制 + 熔断降级（替代Hystrix，支持动态规则） |
| **OpenFeign** | 声明式HTTP远程调用 |
| **Gateway** | API网关（路由转发、鉴权、限流） |
| **Seata** | 分布式事务（AT模式/TCC模式） |


### 24. Nacos服务发现的流程？

**参考回答：**

服务启动时向Nacos注册IP和端口，消费者从Nacos拉取服务列表并缓存到本地。调用时通过LoadBalancer做负载均衡选择一个实例。服务提供者每5秒发一次心跳，Nacos检测到心跳超时（15秒）标记不健康，30秒未恢复则剔除实例。消费者通过定时任务刷新本地缓存，感知实例变化。

Nacos支持临时实例和持久化实例两种模式，临时实例走心跳保活，持久化实例走主动注销。


### 25. Sentinel和Hystrix的区别？

**参考回答：**

Hystrix需要把熔断规则写在代码或配置类里，改了要重启服务；Sentinel支持控制台动态配置规则，改完实时生效，不需要重启服务。Sentinel支持QPS、线程数、关联资源、链路等多种限流维度。Hystrix已进入维护状态，Spring Cloud Alibaba默认用Sentinel。


### 26. Gateway和Nginx的区别？

**参考回答：**

Nginx是流量入口的负载均衡，把请求分给不同的服务集群；Gateway是Spring Cloud的API网关，除了路由转发还负责鉴权、限流、日志这些业务横切逻辑。Gateway可以和注册中心整合，动态感知服务实例变化，不用像Nginx手动更新upstream。


## 七、前端


### 27. Vue2和Vue3的区别？

**参考回答：**

- 响应式：Vue2用defineProperty（只能劫持已有属性），Vue3用Proxy（代理整个对象，新增/删除都能监听到）
- API风格：Vue2是Options API（data/methods/computed分开放），Vue3引入Composition API（按逻辑功能组织）
- 根节点：Vue2单根，Vue3多根（Fragment）
- TS支持：Vue3原生支持更好
- 生命周期：Vue2的beforeDestroy/destroyed → Vue3的onBeforeUnmount/onUnmounted


### 28. v-if和v-show的区别？

v-if：条件为false时不渲染DOM（适合运行时很少改变的场景）。v-show：始终渲染，通过display:none控制（适合频繁切换的场景）。一句话：v-if是“要不要”，v-show是“给不给看”。


### 29. Vue组件通信方式有哪些？

|------|----------|
| props/emit | 父子通信 |
| v-model | 父子双向绑定 |
| provide/inject | 跨层级（祖孙） |
| Pinia/Vuex | 全局状态 |
| mitt | 任意组件（事件总线） |
| $refs | 父调子方法 |


### 30. nextTick的作用？

Vue是异步更新DOM的，改了数据DOM不会立刻更新，nextTick等DOM更新完再执行回调。适合需要操作更新后DOM的场景，比如获取元素高度、滚动位置。
