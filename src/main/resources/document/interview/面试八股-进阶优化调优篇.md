# 进阶优化调优篇 —— 拉开差距


## 一、架构设计


### 1. 如何设计一个支撑万人同时在线的打卡系统？

**参考回答（结合你的EHR考勤和IoT设备经验）：**

接入层：Nginx负载均衡 + CDN加速静态资源。

网关层：Gateway路由转发 + Sentinel限流（单机QPS阈值）。

服务层：按业务域拆分服务（用户服务、打卡服务、统计服务、通知服务），通过Nacos完成服务发现和配置管理。

数据层：打卡记录按月分表，用Redis存当日打卡状态（读多写少），MySQL存全量数据。打卡数据用QoS 2保证不丢不重，断线时用Clean Session=false补推离线消息。

缓存策略：Redis缓存热数据（今日打卡状态）+ Caffeine本地缓存配置信息，多级缓存降低DB压力。

异步解耦：打卡成功后发MQ异步处理统计更新，不阻塞主流程。

容灾：Redis主从 + MySQL主从，任一节点故障自动切换。

监控告警：接口耗时、错误率、QPS配置告警，慢查询自动记录。


### 2. 如何设计一个高可用的微服务架构？

**参考回答：**

从三个层面保证高可用：

服务层面：多节点部署 + 健康检查自动摘除不健康节点；核心服务熔断降级（Sentinel），非核心服务挂了不影响主链路；服务间调用设置超时和重试。

数据层面：MySQL主从复制 + 每日全量备份；Redis主从 + 哨兵自动故障转移；数据定期同步到灾备机房。

运维层面：Docker容器化 + K8s管理，支持滚动更新和自动重启；监控告警（Prometheus + Grafana）覆盖接口耗时、错误率、系统资源；灰度发布，先发一台观察10分钟没问题再全量。


### 3. 如何设计一个秒杀系统？

**参考回答：**

①**流量削峰**：前端限流（按钮置灰、验证码）、网关层限流（Sentinel限流）、MQ削峰（请求先入队，消费者按能力处理）

②**缓存策略**：Redis预热库存（秒杀开始前把库存加载到Redis），扣库存走Redis Lua脚本保证原子性

③**异步下单**：扣库存成功后发MQ异步创建订单，用户先看到“排队中”，后台慢慢处理

④**兜底方案**：Redis挂了走数据库兜底，虽然慢但业务不中断；MQ挂了直接拒绝请求，不把系统打挂


## 二、数据库深度


### 4. 分库分表的设计思路？

**参考回答：**

什么时候需要分库分表：单表数据量超千万或单库QPS超2000时考虑。

方案：垂直分库——按业务域拆分（用户库、订单库）；水平分表——按规则拆分（用户ID取模、时间范围）。

常用中间件：ShardingSphere-JDBC（轻量，适合应用层集成）。

分库分表后要解决的问题：跨库JOIN（走ES或宽表）、分布式ID生成（雪花算法）、分布式事务（最终一致性）。

结合你的简历：目前EHR系统数据量还没到需要分表的程度，考勤明细通过索引优化和定时归档（历史数据迁移到归档表）保持主表数据量可控。


### 5. 读写分离怎么实现？有什么问题？

**参考回答：**

主库处理写操作，从库处理读操作，分散压力。实现方式：应用层硬编码、中间件代理（MyCat/ShardingSphere）、云数据库自带。

需要处理的问题：
①主从延迟——关键数据读主库、监控延迟阈值（超过5秒告警）、非关键查询容忍延迟
②主库挂了——自动故障转移，从库提升为主库
③从库挂了——从数据源列表中移除，读请求回退到主库
④事务内的查询——@Transactional强制走主库


### 6. MySQL主从复制原理？

**参考回答：**

Master把数据变更写入binlog；Slave的IO线程从Master拉取binlog，写入本地relay log；Slave的SQL线程重放relay log，完成数据同步。Slave默认是单线程重放，MySQL 5.6后支持多线程并行复制。

binlog有三种格式：Statement（记录SQL语句）、Row（记录行变更）、Mixed（混合模式）。Row格式最安全但日志量大，Statement格式日志量小但可能主从数据不一致。


## 三、高并发


### 7. 高并发场景下，消息队列怎么用？

**参考回答：**

高并发下MQ的核心作用：削峰、解耦、异步。

削峰：流量瞬间暴涨时，请求先写入MQ，消费者按自身能力慢慢拉取，不会一下把DB冲垮。

异步解耦：核心链路（如下单）完成后发MQ，非核心逻辑（发短信、写日志）后台慢慢处理，不阻塞主流程。

保证消息不丢失三环节：生产者confirm确认、Broker持久化、消费者手动ACK。

消息积压处理：先定位原因（消费能力不足还是上报频率过高），短期增加消费者并发度，长期优化上报策略。


### 8. 高并发下如何保证接口幂等性？

**参考回答：**

幂等性保证方式：
①数据库唯一索引——重复插入会失败，不会产生脏数据
②Redis分布式锁——相同请求ID加锁，处理完释放
③业务状态机——比如“已支付”状态不能再支付
④Token机制——请求前先拿Token，请求时携带Token，处理完Token失效

结合你的简历：大易API对接中间件用唯一索引防重，考勤数据处理也是通过业务ID+状态判断，已处理过的直接跳过。


## 四、容器化


### 9. Docker和K8s的区别？你在项目里怎么用的？

**参考回答：**

Docker是容器化技术，负责把应用打包成镜像并在单机上运行；K8s是容器编排平台，负责在多台机器上管理容器的部署、扩缩容、服务发现。

结合你的简历：目前在用Docker容器化部署，了解K8s核心概念（Pod/Deployment/Service/ConfigMap/Ingress/HPA），但还没到生产级运维的熟练程度。


### 10. CI/CD流程是怎样的？

**参考回答：**

开发提交代码到Git → Webhook触发Jenkins/GitLab CI拉取代码 → 执行maven构建 + 单元测试 → 构建Docker镜像并推送到镜像仓库 → 部署到测试环境（K8s apply）→ 测试通过后手动触发生产发布。


## 五、架构演进


### 11. 从单体到微服务，你怎么考虑演进路径？

**参考回答：**

不要一步到位拆微服务，按业务优先级逐步拆分。

第一步：先做前后端分离，前端独立部署，后端提供REST API。

第二步：把高频修改的业务模块独立出来，比如把用户模块拆成独立服务。

第三步：逐步拆分其他模块，按业务域划分边界。

第四步：引入网关、注册中心、配置中心、链路追踪等基础设施。

原则：能不拆就不拆，拆了要能独立部署、独立迭代。如果拆了之后两个服务改一个需求要同时改，说明拆错了。


### 12. 如何做技术选型？你的选型原则是什么？

**参考回答：**

看三件事：①能不能解决当前问题；②团队能不能维护（技术栈是否匹配团队现有能力）；③未来半年到一年够不够用。

倾向先选成熟稳定的方案，能解决当前需求、有扩展空间就行。比如之前做数据同步，没有盲目上大厂方案，先用Spring Boot + MySQL中间表的方式跑通，等业务量起来再考虑升级。

判断一个方案合不合适，看三点：①能不能解决当前问题；②团队能不能维护；③未来半年到一年够不够用。


## 六、综合场景


### 13. 线上服务突然很慢，怎么排查？

**参考回答：**

①先看监控告警——CPU/内存/IO哪个指标异常
②看日志——有没有大量报错或慢SQL
③看连接池和线程池——是否打满
④看外部依赖——数据库、Redis、下游服务是不是响应变慢
⑤如果都正常——看是否有大流量突发或定时任务集中执行

结合你的简历：上一次类似情况是考勤明细表缺索引导致全表扫描，EXPLAIN定位后加索引恢复。


### 14. 如何设计一个配置中心？

**参考回答：**

可以借鉴Nacos的设计思路：

存储层：配置信息存储在MySQL，支持版本管理和历史回滚。

缓存层：Redis缓存热点配置，降低DB压力。

推送层：配置变更时通过长轮询或WebSocket推送到客户端，客户端本地缓存。

客户端：启动时拉取全量配置，运行时监听配置变更，动态刷新（如@RefreshScope）。

权限控制：配置按环境（dev/test/prod）隔离，不同用户有不同权限。
